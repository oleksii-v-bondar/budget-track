# Budget Track — Sub-project #1: Core Budgeting — Design

Date: 2026-11-19
Status: Approved design, pending implementation plan

## 0. Context and roadmap

Budget Track is a personal, single-user clone of YNAB, hosted in the cloud and used from a phone browser.
"Full YNAB" is split into independent sub-projects, each with its own spec → plan → build cycle:

1. **Core budgeting** (this spec): accounts, transactions, zero-based budget, credit cards, targets, scheduled
   transactions, payees, loans, multi-currency tracking, undo, auth.
2. **Bank sync via Mastercard Open Banking**: consent/account linking, transaction import, matching/dedup, approval
   queue, payee rename rules. This spec reserves `import_id` / `external_id` columns and the `approved` flag for it.
3. **Reports**: spending, income vs expense, net worth, Age of Money.
4. **Extras**: CSV/OFX import, YNAB migration (API/CSV), loan what-if planner, multiple budgets, offline support.

## 1. Decisions summary

| Topic | Decision |
|---|---|
| Users | Exactly one user (the owner) |
| Stack | TypeScript end to end: Vite React PWA + Hono API + Drizzle ORM + Postgres 16 |
| Architecture | Single repo, single `package.json`, single Docker image; budget engine is a pure TS module; balances computed on read |
| Client | Online-only installable PWA; phone layout only (desktop shows the phone layout centered, max ~480px) |
| Currency | Budget currency PLN; foreign-currency accounts allowed, every transaction stores native amount + PLN base amount + FX rate |
| FX source | NBP table A mid rate for the transaction date (falls back to the last published day), manual override |
| Auth | Password + TOTP, recovery codes |
| Hosting | Undecided; deliverable is a portable Docker image + `docker-compose.yml` |
| UI language | English; Polish number/currency formatting (`1 234,56 zł`), dates `dd.MM.yyyy` |
| Time zone | `Europe/Warsaw` for "today", scheduled jobs and month boundaries |

## 2. Architecture

```
src/engine/   Pure TS budget engine with no I/O: money, months, budget math,
              credit-card funding, targets, schedules, loans, auto-assign.
              Must not import from server/ or web/.
src/shared/   zod schemas and DTO types shared by server and web
src/server/   Hono app: routes → command handlers → Drizzle repositories;
              auth, undo log, jobs, NBP client
src/web/      Vite React PWA: TanStack Router + TanStack Query, Hono RPC client,
              Tailwind CSS, vite-plugin-pwa, dnd-kit
drizzle/      SQL migrations (generated by drizzle-kit, applied on startup)
Dockerfile, docker-compose.yml
```

**Runtime:** one Node 22 process (`@hono/node-server`) serves the built PWA as static files plus `/api/*`.
Supporting libraries: `postgres` (postgres.js) driver, zod, pino, croner, otplib, `@node-rs/argon2`.

**Write path:** UI → typed Hono RPC call → command handler. Inside one DB transaction the handler validates
input (zod), applies domain rules, writes rows through a `ChangeRecorder`, and appends an `undo_entry`. The
response carries the IDs of affected entities, and the web app invalidates the matching TanStack Query keys.
Mutations wait for the server (no optimistic updates).

**Read path (budget):** the month-view endpoint runs a few SQL aggregates over a ledger view (§4.6): activity per
(month, category, account class, credit account), card-side transfer totals per (card, month), income per month,
plus assignments, targets and loan data. It passes them to `engine.computeBudget()`, which returns every month from
budget start to the requested month plus any later month that has assignments. The engine recomputes from the start
on each request; at single-user scale (≈10 years × 150 categories) this is well under 50 ms. No balance or
`available` value is persisted.

**Conventions**
- Money is integer grosze (minor units): `bigint` in Postgres, `number` in TS (safe below 2^53). Native amounts
  of foreign accounts are integer minor units of that currency (all NBP table A currencies used here have 2 decimals).
- FX rates are `numeric(14,6)` in DB and decimal strings in TS. Conversion uses integer math (rate scaled to 10^6)
  and rounds half away from zero.
- Dates are calendar dates (`date` type, no time). Months are represented as the first day of the month.
- Sign convention: positive = inflow, negative = outflow, from the account's perspective.

**Config (env):** `DATABASE_URL`, `ENCRYPTION_KEY` (32-byte key, base64, AES-256-GCM for the TOTP secret), `SETUP_TOKEN`,
`TZ=Europe/Warsaw`, `PORT`, `COOKIE_SECURE` (default true), `TRUST_PROXY` (default false; take the client IP from
`X-Forwarded-For`), `LOG_LEVEL`, `MIGRATIONS_DIR`, `NBP_BASE_URL` (default `https://api.nbp.pl`). Sessions are opaque
random tokens stored hashed, so no session-signing secret is needed.

## 3. Domain concepts

**Account classes** (derived from `account.type`):
- **cash**: checking, savings, cash. On-budget.
- **credit**: credit_card, line_of_credit. On-budget, with an auto-created credit card payment category.
- **tracking**: mortgage, auto_loan, student_loan, personal_loan, medical_debt, other_debt (the **loan** types),
  other_asset, other_liability. Off-budget.

An account's type can only change within its class.

**System categories** live in a hidden `internal` group and never appear as editable rows:
- **Ready to Assign (RTA)**: the category for income.
- **Uncategorized**: used for on-budget, non-transfer, non-starting-balance transactions with no category. It
  appears in the budget grid only when it has activity or a non-zero Available in the viewed month (an uncategorized
  inflow carries over), and normal overspending rules apply to it.

Neither system category can receive assignments. "Move money to/from Ready to Assign" changes the other category's
Assigned amount.

## 4. Data model

All tables use UUID primary keys and `created_at` / `updated_at` timestamps unless noted. The exceptions:
`login_attempt` and `undo_entry` have bigserial ids; `assignment`, `loan_interest_override`, `fx_rate`, `month_note` and
`target` use the natural keys listed below; `session` and `undo_entry` have only `created_at`; `login_attempt` has only
`at`; `assignment`, `loan_interest_override`, `fx_rate` and `scheduled_subtransaction` have no timestamps.
Timestamps have millisecond precision (`timestamptz(3)`), so a JS `Date` round-trips exactly through undo images.
Foreign keys have no `ON DELETE` actions: commands delete or re-point child rows themselves, so the undo log sees every
change.

### 4.1 Settings and auth
- `app_user` (at most one row): `password_hash` (argon2id), `totp_secret_enc`, `recovery_code_hashes text[]`,
  `base_currency` (`PLN`), `budget_start_month`.
- `session`: `token_hash` (SHA-256 of a 256-bit random token), `expires_at`, `last_seen_at`, `user_agent`.
- `login_attempt`: `at`, `success`, `ip` (for rate limiting and lockout).

### 4.2 Accounts
- `account`: `name`, `type` (enum from §3), `currency` (ISO code, default `PLN`), `closed`, `sort_order`, `note`,
  `last_reconciled_at`, `last_reconciled_balance`.
  `account_class` is a generated column (cash / credit / tracking) derived from `type`.
  Loan-type columns: `interest_rate` (APR, `numeric(7,4)`), `min_payment`, `escrow_amount`, `paired_category_id`.
  Credit-class accounts (`credit_card`, `line_of_credit`) also get optional `interest_rate` and `min_payment`
  columns, used by debt targets on their credit card payment category.
- `loan_interest_override`: `account_id`, `month`, `amount`. Exists only when the user edits the computed interest.

### 4.3 Categories and budget
- `category_group`: `name`, `sort_order`, `hidden`, `kind` (`normal` | `cc_payments` | `debt_payments` | `internal`;
  at most one group of each kind other than `normal`), `deleted_at`.
- `category`: `group_id`, `name`, `sort_order`, `hidden`, `note`, `system_kind` (`rta` | `uncategorized` | null),
  `linked_account_id` (set for credit card payment categories and paired loan categories), `deleted_at`.
- `assignment`: PK (`category_id`, `month`), `amount`. Sparse: rows with amount 0 are deleted.
- `target` (0..1 per category):
  - `kind`: `spending` | `balance` | `debt`
  - `cadence`: `weekly` | `monthly` | `yearly` | `custom` | `none`
  - `amount`, `mode` (`set_aside` | `refill`, used by spending targets)
  - `due_weekday` (0–6, 0 = Sunday), `due_day_of_month` (1–31 or null = last day), `due_date`
  - `repeat_unit` (`month` | `year` | null), `repeat_every` (int), `start_month`
  - `debt_mode` (`min_payment` | `fixed` | `payoff_by_date`)
  - `snoozed_month`
- `month_note`: PK `month`, `note`.

### 4.4 Payees and transactions
- `payee`: `name` (unique among live user payees; transfer and system payees are exempt), `transfer_account_id`
  (unique; one auto-created "Transfer : <Account>" payee per account), `system_kind` (`starting_balance` |
  `reconciliation_adjustment` | `fx_revaluation` | null; one payee per kind, created by migration), `last_category_id`,
  `deleted_at`.
- `transaction`:
  - `account_id`, `date`, `payee_id`, `category_id` (null for splits, budget↔budget transfers, tracking-only
    transactions, credit/tracking starting balances), `memo`
  - `amount` (native), `amount_base` (PLN), `fx_rate`, `fx_rate_manual` (bool). Entered amounts (transaction, transfer
    other side, split line, starting balance, reconcile statement balance, interest override) are capped at ±10^13
    minor units (100 bn zł) and computed PLN amounts at ±10^14 (including bases converted at an NBP rate, reconcile
    adjustments and FX revaluations), so sums over many rows stay exact below 2^53.
  - `cleared` (`uncleared` | `cleared` | `reconciled`), `approved` (bool), `flag` (`red` | `orange` | `yellow` |
    `green` | `blue` | `purple` | null)
  - `transfer_account_id`, `transfer_txn_id`, `transfer_subtxn_id`
  - `is_split`, `is_starting_balance`, `scheduled_id`
  - `import_id`, `external_id` (unique per account where not null; reserved for #2)
  - `deleted_at`
- `subtransaction`: `txn_id`, `amount`, `amount_base`, `category_id`, `payee_id`, `memo`, `transfer_account_id`,
  `transfer_txn_id`, `sort_order`, `deleted_at`.
- `scheduled_transaction`: same template fields as `transaction` except cleared/approved and `amount_base` (the PLN amount is computed when an occurrence is entered), plus `frequency`,
  `anchor_date`, `next_date`.
  Frequencies: `once`, `daily`, `weekly`, `every_other_week`, `twice_a_month`, `every_4_weeks`, `monthly`,
  `every_other_month`, `every_3_months`, `every_4_months`, `twice_a_year`, `yearly`, `every_other_year`.
- `scheduled_subtransaction`: mirrors `subtransaction` except `amount_base`, `transfer_txn_id`, timestamps and
  `deleted_at` (template rows are hard-deleted).

### 4.5 Support
- `fx_rate`: PK (`currency`, `date`), `rate`, `source` (`nbp`), `effective_date` (the NBP publication day used).
- `undo_entry`: `label`, `changes jsonb` (ordered `[{table, pk, before, after}]`; `pk` is an object because
  `assignment` has a composite key), `state` (`done` | `undone`).

### 4.6 Ledger view
`v_ledger_line` merges non-split transactions and subtransactions of non-deleted transactions (all accounts) into one
row per line: `account_id`, `account_class`, `date`, `month`, `category_id`, `amount_base`,
`is_transfer`, `counter_account_class`, `txn_id`, `subtxn_id`. Split parents are excluded, and their lines inherit the
parent's account and date. All engine aggregates come from this view.
The view also exposes the native `amount` and `is_starting_balance`.

## 5. Budget engine rules

All amounts are PLN base. `m` = month, `c` = category.

### 5.1 Activity, Available, Carry
- **Activity(c,m)** = Σ `amount_base` of ledger lines in on-budget accounts with category `c` in month `m`. This
  includes categorized transfers to tracking accounts (e.g. loan payments) and lines of split transactions.
- **Available(c,m)** = Carry(c,m) + Assigned(c,m) + Activity(c,m)
- **Carry(c,m)** = max(0, Available(c,m−1)). Negative Available never carries over.
- Budget start month = min(`budget_start_month`, month of the earliest transaction). Assignments and month notes may
  still exist before it (e.g. after the account with the earliest transaction is deleted); those months stay editable
  and reachable in the month switcher (its first month is the earliest such month), and the budget computation widens
  its range back to the earliest such month.
- Hidden categories behave identically; they are only hidden in the UI.

### 5.2 Overspending (cash vs credit)
For category `c` in month `m` with Available < 0, let `O = −Available(c,m)`:
- `creditSpend(k)` = max(0, −Σ amounts of `c`'s lines on credit account `k` in `m`)
- **creditOver** = min(O, Σₖ creditSpend(k)), split across cards in proportion to creditSpend(k), with
  largest-remainder rounding to the grosz (ties go to the earlier card in input order).
- **cashOver** = O − creditOver. This also covers overspending with no card spending behind it, e.g. from a negative
  assignment.
- **Why (YNAB rule):** available money covers cash spending first, because that cash has already left the bank.
  So when overspending is mixed, the cash part is overspent first and the category shows **red**. Covering it removes
  the cash part first, after which it shows **yellow** until fully covered.
- **Color**: red if cashOver > 0, otherwise yellow if creditOver > 0.
- **CashOverspent(m)** = Σ cashOver over all categories (including credit card payment and Uncategorized).

### 5.3 Credit card payment categories
Each credit-class account `k` has payment category `p_k` (group kind `cc_payments`).

**Activity(p_k, m)** is the sum of:
- **Funded spending**: for every category `c` other than RTA (Uncategorized included) with net card-`k` lines in `m`,
  let `net = −Σ amounts of c's lines on k in m`.
  - If `net > 0`: add `net − creditOver(c,k,m)`.
  - If `net < 0` (a net refund): add `net`, which moves money back out of `p_k`.
- **Transfers between `k` and any on-budget account**: subtract the card-side amount. A payment of X (card side +X)
  gives −X; a cash advance or balance transfer out (card side −X) gives +X.

Further rules:
- `p_k` follows the same Available, carry and overspending rules. A payment larger than Available causes red cash
  overspending, which is deducted from RTA next month.
- Inflows on `k` categorized to RTA count as income and don't touch `p_k`.
- The starting balance of a credit account is not categorized and doesn't affect the budget. The inspector shows
  **"Need X to pay in full"** = max(0, −balance(k) − Available(p_k, m)), with balance(k) in PLN at the end of `m`
  (or today, if that is earlier).
- Credit overspending is not carried: next month the category resets to 0, and the unfunded debt stays visible
  through "Need X to pay in full".
- **Known simplification vs YNAB:** flows are computed from monthly net amounts and always apply. YNAB skips the
  flow while a card has a positive (credit) balance. Here, a refund on a card in credit can make `p_k` negative
  (red), which the user fixes by moving money.

### 5.4 Ready to Assign
- **Income(m)** = Σ `amount_base` of on-budget ledger lines categorized RTA in `m`. This includes starting balances of
  cash-class accounts and tracking → budget transfers categorized to RTA.
- **AssignedTotal(m)** = Σ Assigned(c,m) over all categories.
- **Leftover(m)** = Leftover(m−1) + Income(m) − AssignedTotal(m) − CashOverspent(m−1), with Leftover(start−1) = 0.
  A negative Leftover carries forward.
- **Shown RTA(m)** = Leftover(m) − Σ_{m' > m} AssignedTotal(m')
- The RTA breakdown shows: left over from last month, income this month, assigned this month, assigned in future
  months, cash overspent last month.

### 5.5 Transfers and categorization rules (validated server-side)

| From \ To | budget (cash/credit) | tracking |
|---|---|---|
| budget | no category on either side | budget side requires a category (or split lines) |
| tracking | budget side requires a category (usually RTA) | no category |

- Tracking-account lines never carry a category.
- No transaction line may be categorized to a credit card payment category. Those categories change only through
  funded spending flows, card transfers and assignments.
- An on-budget, non-transfer, non-starting-balance transaction without a category is "Uncategorized".
- A line may use Ready to Assign, a regular category or a loan's paired category (hidden ones included). Uncategorized
  is never chosen explicitly: leaving the category empty means Uncategorized.
- The category of a budget↔tracking transfer (or transfer line) is stored on its budget side, whichever side it was
  entered from. Closed accounts take no new rows; rows already there stay editable.

### 5.6 Future-dated transactions
A transaction saved with `date > today` is stored as a `scheduled_transaction` with frequency `once`. The budget only
ever includes transactions dated today or earlier. The UI allows navigating up to 24 months ahead; the engine has no
limit.

### 5.7 Invariant (property-tested)
For every month `m` up to the current month:

Σ PLN-base balances of cash-class accounts at end of `m`
  = Σ_c Available(c,m) + Leftover(m) + Σ_c creditOver(c,m) − K(m)

- `c` ranges over all non-RTA categories, including credit card payment and Uncategorized.
- K(m) = cumulative Σ `amount_base` of RTA-categorized lines on credit-class accounts dated ≤ end of `m` (e.g. card
  cashback booked as income, or FX revaluation of a foreign card).
- Credit overspending in `m` is card spending that no cash has funded yet, so it's added back. At rollover the
  category resets to 0 and the term disappears.
- Positive Available in a credit card payment category is cash set aside for card debt.

## 6. Targets

The engine computes `need(c,m)`, `underfunded(c,m)` and `progress(c,m)` for categories that have a target.
`A` = target amount; "ceil" rounds up to the grosz.

| Kind / cadence | need(c,m) | underfunded(c,m) |
|---|---|---|
| spending, weekly on weekday d | A × (number of weekday d in m) | set_aside: max(0, need − Assigned); refill: max(0, need − (Carry + Assigned)) |
| spending, monthly by day n | A | same as weekly |
| spending, yearly / custom (due date D) | ceil(max(0, A − fundedBefore) / monthsLeft) | max(0, need − Assigned) |
| balance, no date | max(0, A − Carry) | max(0, A − Available) |
| balance, by date D | ceil(max(0, A − Carry) / monthsLeft) | max(0, need − Assigned) |
| debt, min_payment | account.min_payment | max(0, need − Assigned) |
| debt, fixed | A | max(0, need − Assigned) |
| debt, payoff_by_date D | amortized payment of max(0, −balance at start of m) at APR/12 over monthsLeft, plus account.escrow_amount (loans only); 0 when nothing is owed (escrow is not added) | max(0, need − Assigned) |

Yearly and custom targets:
- **Next due date** = the first occurrence of D (advanced by `repeat_every` × `repeat_unit`) whose month ≥ m.
- **monthsLeft** = number of months from m to that due month, inclusive (≥ 1).
- **fundedBefore**:
  - refill: Carry(c,m)
  - set_aside: Σ Assigned in this cycle's months before m. A cycle starts the month after the previous due month, or
    at `start_month` for the first cycle.
- A non-repeating target past its due month has need = max(0, A − fundedBefore), all of it in m (overdue).
- Yearly is custom with `repeat_every = 1, repeat_unit = year`.

Other target rules:
- Debt targets apply to credit card payment and loan-paired categories. They count only direct assignments, so
  for a credit card the amount is "in addition to funded spending".
- The balance at the start of m is the account's PLN balance before m (counting transactions dated today or
  earlier). If the account has no minimum payment (`min_payment`) or no APR (`payoff_by_date`), the missing value
  counts as 0 and the target is flagged **incomplete** until the user enters it.
- A loan's balance includes the interest and escrow charged (§8): the balance at the start of m counts the charges of
  the months before m. For a foreign-currency card or loan, the minimum payment and escrow (in the account's currency)
  are converted to PLN at the latest NBP rate (§9); without a rate they count as 0 and a `min_payment` or
  `payoff_by_date` target is flagged **incomplete** (a `fixed` target doesn't use them).
- **Progress** = (need − underfunded) / need, or Available / A for balance targets.
- **Snooze:** if `snoozed_month = m`, underfunded is 0 and the category matches the "Snoozed" filter. Progress for a
  snoozed target still reflects its real funding (it is computed from the unsnoozed underfunded amount).
- **Available pill color**, in order: red = cash overspending; yellow = credit overspending or underfunded > 0;
  green = Available > 0 or target met; grey otherwise. "Target met" requires need > 0, underfunded = 0 and the
  target not snoozed in m.
- **Overfunded filter:** has a target and Assigned(c,m) > need(c,m).

## 7. Auto-assign

Scope can be all visible categories (visible categories of visible groups), one group, or one category; a group or
category scope includes hidden categories. Ready to Assign and Uncategorized are never in scope. Strategies:
- **Underfunded**: walk categories in display order and assign `underfunded(c,m)`, capped at the remaining Shown
  RTA(m). Stop when RTA reaches 0.
- **Assigned last month**: set Assigned(c,m) = Assigned(c,m−1).
- **Spent last month**: set Assigned(c,m) = max(0, −Activity(c,m−1)).
- **Average assigned / Average spent**: the average over the previous up to 12 months that exist since budget start
  (excluding m), rounded to the grosz. Average spent = max(0, −round(average of net Activity(c, month))) over that
  window, so net refunds reduce it.
- **Reset available**: Assigned(c,m) −= Available(c,m), which brings Available to 0.
- **Reset assigned**: Assigned(c,m) = 0.

All strategies except Underfunded may push RTA negative. Each auto-assign run is one undoable command.

## 8. Loans (tracking accounts with loan types)

**Interest and escrow**
- The engine's input per month is `LoanMonthInput` = {`transactionsTotal`, `paymentsTotal`}: Σ of all the loan
  account's transaction amounts in m, and Σ of its inflows (payments) in m.
- A **payment** is an inflow to the loan account in month `m`, typically a categorized transfer, whose payee isn't a
  system payee: the starting balance, reconciliation adjustments and FX revaluations count in `transactionsTotal` but
  never as payments. Month `m` has a payment iff `paymentsTotal` > 0.
- If month `m` has at least one payment, the engine applies:
  - `interest(m)` = override(m) ?? round(|balance at start of m| × APR / 12)
  - `escrow(m)` = account.escrow_amount
- **End-of-month balance** = start balance + Σ transaction amounts − interest(m) − escrow(m). Escrow covers fees and
  doesn't reduce principal.
- Principal reduction per month = paymentsTotal − interest − escrow.
- APR must be ≥ 0; the engine rejects a negative APR.
- The register shows synthetic read-only "Interest charge" / "Escrow" rows per month. Editing the interest row writes
  a `loan_interest_override`.
- The loan's displayed balances (accounts list, register header, reconcile, close, debt targets, loan panel) include
  the interest and escrow charged. A month's charges are cleared once every payment in that month is cleared, and
  uncleared while any of them is uncleared. The loan engine runs in the loan's currency; a foreign loan's charges are
  converted to PLN at the rate its payments that month were booked at.
- `GET /api/accounts/:id/loan` returns the months with their interest, escrow and principal. A month's synthetic rows
  are dated on its first payment (`chargedOn`) and cleared as above (`chargesCleared`, true in a month without a
  payment); the register interleaves them by date, and its cursor paging over transactions is unchanged.
- An interest override is set for a month from the loan's first transaction to the current month, in the loan's
  currency (0 … 10^13, like entered amounts, §4.4). It applies in months with a payment, and later months' interest
  follows the new balance.
- A loan's first month has no interest, even with a payment in it, because its balance at the start of that month is
  0 (escrow is still charged). An interest override for that month adds it.

**Payoff and inspector**
- **Projected payoff date**: amortize from the current balance at APR/12 using the debt target amount (or
  `min_payment` if there's no target). Show "Never" if the payment minus escrow doesn't exceed the monthly interest,
  or if payoff would take more than 1200 months.
- **Amortized payment** (used by `payoff_by_date` targets): the minimal whole-grosz monthly payment that the
  month-by-month projection (with interest rounded each month, as above) confirms pays the debt off within the term.
- **Paired category**: when creating a loan, the user can opt in to a category in the "Debt Payments" group
  (`linked_account_id` = loan) with a `debt/min_payment` target.
- The paired category's inspector shows balance, APR, minimum payment, projected payoff date and a **Record payment**
  shortcut. The shortcut opens the transaction sheet prefilled: transfer from the last-used cash account to the loan,
  category = paired category, amount = target need.
- The panel is part of the month view (`loan` on the paired category). The projection starts in the current month,
  or the next one once this month has a payment (as defined above, so a reconciliation adjustment doesn't count); it
  uses a `fixed` or `payoff_by_date` target's need, otherwise the minimum payment (a foreign loan converts the need
  back at the latest rate, and uses the minimum payment without one). "Last-used cash account" is the open cash
  account of the latest transfer into the loan, else the first open cash account; the amount is −need (PLN).

## 9. Multi-currency (FX)

- Non-PLN accounts store the native `amount` and `amount_base = round(amount × fx_rate)`.
- **Default rate**: NBP table A mid for the transaction date
  (`https://api.nbp.pl/api/exchangerates/rates/A/{code}/{date}/?format=json`). On 404, step back one day at a time,
  up to 7 days. Results are cached in `fx_rate`.
- The user can override the rate (`fx_rate_manual = true`). Changing the date re-fetches the rate unless it's manual.
- Unsupported currency or NBP unreachable → the rate field is required and the UI asks for it.
- **NBP client**: one quote tries the date and up to 7 earlier days within a 5 s timeout; any other error, a malformed
  answer or a timeout means "no rate". Only final rates are cached: published that day, or for a past day or a
  weekend. Quotes run before a command or read transaction starts, never inside one; PLN is never quoted. Rates keep
  6 decimals (§2), so a currency quoted far below 1 zł loses precision (IDR's mid 0.00022236 is stored as 0.000222);
  this is accepted unless the rate scale is widened.
- Writes (transactions, foreign starting balances, reconcile adjustments) resolve the default rate before the
  command: a sent rate is manual (`fx_rate_manual = true`), an NBP rate is not. Without either, the answer is 422
  `fx_rate_required`. A base converted at either rate stays within the §4.4 cap (422 `amount_too_large`). A
  future-dated transaction (a schedule, §5.6) stores the rate sent, or none: its occurrence gets the NBP rate of the
  day it is entered. An edit keeps the stored rate unless a new one is sent, except that a new date replaces an NBP
  rate with that day's. Bulk edits never change dates and use stored rates only. `GET /api/fx/rates/:currency/:date`
  gives the sheet the NBP rate (no future dates).
- "Latest available NBP rate" is today's quote (falling back like any quote). Account reads quote it once per foreign
  currency per request; so do the month view and auto-assign for foreign linked accounts (§6).
- **Split lines** use the parent's rate. The rounding remainder goes to the last line so that
  Σ line base = parent base.
- **Cross-currency transfers**: the user enters both actual amounts.
  - PLN ↔ foreign: the foreign side's `amount_base` = −(PLN side amount).
  - Foreign ↔ foreign: the source side's base comes from its rate; destination base = −source base. The rate is
    stored on the source side; a side whose base is derived from the other side stores `fx_rate = null`.
  - Either way the transfer nets to 0 in the budget. The effective rate is displayed.
  - Split lines transfer only to accounts in the same currency (counterpart base = −line base).
- **Account display**: native balance, plus "≈ X zł" at the latest available NBP rate.
- **Revalue**: unrealized difference = round(native balance × latest rate) − Σ `amount_base`. The action posts a
  transaction with `amount = 0`, `amount_base = diff`, payee "FX revaluation", cleared. On-budget accounts get
  category RTA; tracking accounts get no category.
  It takes an optional manual rate (else the latest NBP rate) and is refused for PLN and closed accounts and when the
  difference is 0; a difference above the §4.4 cap is 422 `amount_too_large` (on `fxRate`). A revaluation keeps its
  amounts: only its memo, flag, cleared and approved status change (`revaluation_fixed` otherwise); deleting it takes
  it back.
- Reconciliation uses native amounts.

## 10. Transactions and related workflows

**Creating and editing**
- Manual transactions are created `approved = true`. The `approved = false` state exists for bank import (#2).
- Saving a categorized, non-transfer transaction updates `payee.last_category_id`. The transaction sheet pre-fills
  the category from the selected payee. An edit updates it only when the payee or the category changes.
- A saved transaction can move to another account in the same currency; every rule is checked again. It can't move to
  a date after today (§5.6 applies to new transactions).

**Splits**
- A split has `is_split = true`, a null parent category, ≥ 2 lines, and Σ line amounts = parent amount.
- A line may be a transfer, which creates a counterpart transaction in the target account with `transfer_txn_id`
  pointing to the parent and `transfer_subtxn_id` to the line.
- Editing lines replaces them: the old lines and their counterparts are soft-deleted, unless the lines sent are
  identical. Edits of the split's date or account update its line counterparts in place.
- A line's counterpart takes only memo (mirrored to the line), cleared, approved and flag; the rest is edited on the
  split, and the counterpart goes away by removing its line.

**Transfers**
- Creating a transfer creates both sides atomically, linked via `transfer_txn_id`.
- Editing date, amount or memo on one side mirrors it to the other. For cross-currency transfers, the other side's
  native amount is changed only when the user edits it explicitly.
- Cleared status is independent per side. Deleting one side deletes both.
- Choosing a different payee retargets or ends the transfer: the old other side is soft-deleted and a new one created.
- A future-dated transfer between currencies is refused until scheduled transactions can store the other side's
  amount.

**Reconciled transactions**
- Changing amount, account, date or the transfer link of a reconciled transaction requires `confirmReconciled: true`.
  The UI asks for confirmation first. Un-reconciling and deleting it need the confirmation too, and so do mirrored
  changes that reach a reconciled other side. Without it the server answers 409 `confirm_reconciled`.

**Starting balance**
- Created with every new account: payee "Starting Balance", `cleared`, `is_starting_balance = true`, dated on the
  user-chosen date (default today).
- Cash class → category RTA. Credit and tracking → no category.

**Reconcile flow** (per account, native currency): "Is your cleared balance X?"
- **Yes** → all cleared transactions become reconciled; update `last_reconciled_at` and `last_reconciled_balance`.
- **No** → the user enters the statement balance and sees the difference. They can keep reviewing, or "Create
  adjustment & finish". The adjustment is payee "Reconciliation Balance Adjustment", cleared, category RTA (on-budget)
  or none (tracking), after which everything cleared is marked reconciled.
- `POST /api/accounts/:id/reconcile` takes `statementBalance` (an entered amount, capped like the others, §4.4),
  `createAdjustment` and, for a foreign adjustment, an optional `fxRate` (else today's NBP rate). A difference without
  `createAdjustment` is 422 `reconcile_mismatch` with the `difference`; an adjustment whose PLN amount is above the
  §4.4 cap is 422 `amount_too_large` on `statementBalance`. Closed accounts are refused. It is one undoable command; a
  loan's cleared balance includes the interest and escrow of months whose payments are all cleared (§8).

**Scheduled transactions**
- A croner job runs daily at 00:05 Europe/Warsaw and also once at server start (catch-up). For each schedule with
  `next_date ≤ today`, it enters one transaction per due occurrence (uncleared, approved, `scheduled_id` set) and
  advances `next_date`. `once` schedules are deleted after entering.
- Monthly-style frequencies clamp days past month-end to the last day while keeping `anchor_date`.
- `twice_a_month`: anchor day d plus day d+15 (or d−15 and d when d > 15), clamped to month-end.
- User actions: **Enter now** enters the next occurrence today and advances. **Skip** advances without entering.
- Job-made writes create no undo entry and don't clear the redo stack.

**Payees**
- Rename. Merge (reassign all transactions, lines and schedules to the target payee, then soft-delete the source).
  The target keeps its last-used category, or takes the source's when it has none.
- Delete is allowed only when the payee is unused by live rows. Transfer and system payees can't be renamed, merged or
  deleted, and system payees can't be chosen for a transaction.

**Categories**
- Create, rename, reorder (drag), hide, and move between groups.
- **Delete** requires choosing a destination category (a live, normal one). Transactions, lines, schedules, payees'
  last-used category and assignments move there (assignments summed per month), then the category is soft-deleted
  together with its target.
- A group can be deleted only when it has no live categories; groups are soft-deleted.
- Credit card payment and paired loan categories follow their account: they can't be renamed, moved or deleted on
  their own (deleting the account removes them). Credit card payment categories are hidden automatically when the
  account is closed with Available = 0 in the current month. Reopening the account doesn't unhide them.

**Accounts**
- Create via a type-specific wizard. Edit name, note and loan fields.
- Close requires a zero balance; otherwise the UI offers an adjustment transaction first. Reopen is allowed.
- Delete is allowed only when the account has no transactions other than its starting balance.

**Search and bulk operations**
- Register search is server-side and cursor-paginated by (date desc, id).
- Filters: text (ILIKE on payee, memo, category), date range, amount range, account, category, payee, flag, cleared
  state, unapproved.
- Bulk operations on the selected IDs are one command each (one undo): categorize, set payee, set flag,
  clear/unclear, approve, move to account (same-currency accounts only), delete. Each row is checked like a single
  edit; if one fails, nothing changes. A request takes up to 500 IDs.
- The amount range filters the signed native amount.

**Undo/redo**
- Every user command writes through `ChangeRecorder`, which captures the before/after row images.
- **Undo** applies the before images in reverse order; **Redo** applies the after images. Both run in a single DB
  transaction and first check that the current rows equal the expected images. On mismatch the server refuses with
  "Can't undo: data changed since".
- A new user command deletes all `undone` entries (clears redo). Only the newest 100 `done` entries are kept.
- Auth and settings changes are not undoable.

## 12. Security

**First-run setup**
- `/setup` is enabled only while `app_user` is empty and requires `SETUP_TOKEN` (from env), entered on the page.
- Steps: set password (min 12 chars) → scan TOTP QR (otplib, 30 s step, ±1 window) and confirm a code → 10 recovery
  codes shown once (stored as argon2 hashes, single-use).

**Login and sessions**
- Login is password + TOTP code, or password + recovery code.
- Session cookie: httpOnly, Secure, SameSite=Strict, opaque random token; the DB stores its SHA-256. 30-day sliding
  expiry.

**Rate limiting:** 5 login attempts per minute per IP. After 10 consecutive failures, login is locked for 15 minutes.

**Requests**
- All `/api` routes except auth require a session.
- Mutating requests must carry the header `X-Requested-With: budget-track` (CSRF defense on top of SameSite).
- Security headers on all responses: strict CSP (self only), `X-Content-Type-Options`, `Referrer-Policy`,
  `frame-ancestors 'none'`.

**Secrets:** the TOTP secret is encrypted with AES-256-GCM using `ENCRYPTION_KEY`. HTTPS is terminated by the hosting
platform or reverse proxy.

**Settings actions:** "log out all sessions" deletes every session row; changing the password also logs out all other
sessions. Changing the authenticator requires the password plus the current authenticator code or a recovery code, and
signs out other sessions.

## 13. Error handling

- **zod validation failures** → HTTP 400 `{ code: "validation", fieldErrors }`; the UI shows them inline. Field
  errors are keyed by the dotted path of the field (`lines.1.amount`); a domain error about one field (or split
  line, or bulk row: `ids.3`) carries the same `fieldErrors`. An amount above the §4.4 cap is a 400 ("Amount is too
  large.").
- **Domain rule violations** throw a typed `DomainError(code, message)` → HTTP 422; the UI shows the message.
  Examples: split sum mismatch, category on a budget↔budget transfer, closing an account with a non-zero balance,
  a PLN amount above the §4.4 cap (`amount_too_large`, with the field that caused it).
- **Undo/redo conflicts** (a row changed since the command) → HTTP 409 `undo_conflict` "Can't undo: data changed
  since." (or "Can't redo: …"); an empty stack → 409 `nothing_to_undo` / `nothing_to_redo`.
- **Unconfirmed changes to reconciled transactions** → HTTP 409 `confirm_reconciled`; the UI asks and resends with
  `confirmReconciled: true`.
- **Reconcile mismatch** (statement ≠ cleared balance, no adjustment asked for) → HTTP 422 `reconcile_mismatch` with
  `difference` = statement − cleared, in the account's minor units.
- **Auth failures** → 401 (no session) or 429 (rate limited / locked).
- **Unexpected errors** → 500 with a generic message. The server logs details with pino (JSON to stdout, including a
  request ID); the UI shows a toast with Retry.
- Each command runs in exactly one DB transaction (all-or-nothing). Transactions, subtransactions, categories,
  category groups and payees are soft-deleted. The exception is deleting an account (allowed only while nothing else
  refers to it): it hard-deletes the rows created with it, i.e. its starting balance, transfer payee and linked
  categories (with their assignments and target). Otherwise these rows are only ever soft-deleted.
- If the NBP client fails (timeout 5 s), it never blocks a save: the UI requires a manual rate instead.

## 15. Deployment

- Multi-stage `Dockerfile` (build web + server → slim Node 22 runtime, non-root user). Migrations run on startup
  before listening. `GET /healthz` returns DB connectivity status.
